# Документ 05. Запуск на Windows, проверка и передача результатов

## Подготовка рабочей папки

Для запуска второй лабораторной нужно скачать обновлённый репозиторий daya-alexandra/gen-ai и распаковать архив. Рабочая папка называется lab2_text. Командную строку следует открывать именно в ней, поскольку относительные пути к requirements.txt и файлам программы отсчитываются от текущего каталога. Если приглашение командной строки показывает C:\Windows\System32, это другая папка. Запущенная там установка зависимостей не найдёт файл проекта, даже если он виден в Проводнике на рабочем столе.

В Windows CMD для копирования используется команда copy. Команда Copy-Item принадлежит PowerShell и в обычной командной строке не распознаётся. Смешивание примеров для разных оболочек приводит к ошибке, которая не связана ни с Python, ни с ключом API. Поэтому инструкция второй работы содержит команды именно для CMD. Пользователь может запускать их по одной, дожидаясь завершения предыдущей, либо воспользоваться подготовленным сценарием. Путь с пробелами или кириллицей нужно передавать в кавычках, чтобы он воспринимался как один аргумент.

## Автоматический сценарий

Файл RUN_LAB2.cmd сначала переходит в собственную папку командой cd /d и включает PYTHONUTF8=1. Затем при необходимости создаётся виртуальное окружение .venv через установленный Python. После этого зависимости устанавливаются из requirements.txt. Такой порядок помогает избежать прежней ошибки, когда окружение случайно создавалось в системном каталоге. Активация окружения отдельной командой не обязательна: сценарий вызывает конкретный .venv\Scripts\python.exe, поэтому понятно, какой интерпретатор выполняет каждый шаг.

Для проекта требуется Python версии 3.10 или новее. Файл requirements.txt перечисляет Pydantic, библиотеку клиента OpenAI, python-dotenv, matplotlib и numpy. Название библиотеки OpenAI не означает, что запрос отправляется в аккаунт ChatGPT: адрес API и ключ задаются настройками DeepSeek. Эта библиотека используется как совместимый HTTP-клиент. Подписка на обычный чат и доступ к программному API — разные механизмы. Их нельзя считать взаимозаменяемыми только из-за совпадения названия модели или библиотеки.

Если заполненного .env в lab2_text нет, сценарий сначала ищет его в родительской папке, затем в соседней lab1_verified. Найденный файл копируется локально. Если подходящего файла нет, создаётся копия .env.example и открывается Блокнот. В ней нужно заменить PASTE_YOUR_KEY_HERE после LLM_AUTH_TOKEN, сохранить файл и закрыть окно редактора. Пользователь не должен отправлять снимок содержимого ключа в чат. Для диагностики достаточно сообщения об ошибке, где секретное значение не показано.

## Порядок выполнения

После установки зависимостей запускаются локальные тесты test_lab2. Они проверяют поведение программы на специально подготовленных ответах-заглушках и не расходуют токены DeepSeek. Успешный тест не означает, что реальная модель уже проанализировала отзывы. В тестовом отчёте используется явная отметка «ТЕСТОВЫЙ ПРОГОН». Проверяющий скрипт по умолчанию отказывается принимать такой результат за настоящий API-эксперимент. Это защищает от случайной публикации тестовых чисел в качестве лабораторных измерений.

Следующий шаг — pipeline.py. Здесь уже выполняются платные запросы с ключом пользователя. На экране последовательно появляются сообщения об извлечении и аспектах для порций отзывов, о MAP, проверке сводки судьёй и дополнительных темах. Если возникает ошибка, сценарий останавливается и сохраняет готовые ответы. Не нужно удалять весь output, чтобы повторить попытку. После исправления ключа, сети или другой причины тот же сценарий продолжит работу с сохранённого состояния при неизменных коде и данных.

Режим UTF-8 нужен не только для красивого отображения русских букв. Некоторые стандартные операции чтения текста в Windows используют системную кодировку, например cp1251. Файл, сохранённый в UTF-8, может вызвать UnicodeDecodeError или дать неправильные символы при таком чтении. Код проекта явно задаёт UTF-8 для файлов, а сценарий дополнительно включает соответствующий режим интерпретатора. Изменение цвета текста в терминале или повторная установка API-ключа такую проблему кодировки не решает.

## Проверка сохранённого эксперимента

После генерации выполняется verify_results.py. Он заново читает входные отзывы и сравнивает их с сохранённым снимком, проверяет хеши кода, полноту идентификаторов, разбиение на фрагменты и цитаты. Результаты IE, аспектов, MAP, итогового REDUCE и judge сопоставляются с принятыми ответами из кэша и журнала. Кроме того, проверяются токены, расчётная стоимость, наличие тепловой карты и три раздела выводов. Проверка не отправляет новые запросы и не меняет результаты модели.

Если файл с результатом был вручную изменён, например в reviews.json заменён автор, сравнение с принятым ответом должно обнаружить несоответствие. Правка чисел ради более красивого отчёта также разрушает проверяемость эксперимента. Для содержательной доработки следует менять код или промпт и запускать отдельную версию эксперимента. Проверка файлов подтверждает их внутреннюю согласованность, но не обращается к серверным журналам DeepSeek и не является независимым доказательством банковского списания. Эти ограничения нужно сохранять в описании результата.

## Архив и публикация

После успешной проверки collect_results.py собирает lab2_results.zip. В архив включаются файлы JSON, JSONL, PNG и Markdown из каталога output, в том числе кэш принятых ответов, необходимый для аудита. Виртуальное окружение, исходный .env и посторонние файлы рабочего стола не добавляются. Перед передачей архива полезно убедиться, что это именно lab2_results.zip, а не полный архив папки вместе с ключом. Такой порядок уменьшает вероятность случайной отправки секретов и делает проверку результата удобнее.

На GitHub подготовленный код и завершённый эксперимент имеют разные статусы. До реального запуска в output лежит только описание ожидаемых файлов. Нельзя считать лабораторную готовой к сдаче лишь потому, что репозиторий существует и локальные тесты прошли. После запуска нужно проверить числовые критерии, прочитать выводы и убедиться, что примеры ошибок описаны честно. Если все рекомендации в основном прогоне получили supported, нельзя переименовать одну из них в not_supported ради выполнения требования к примеру.

Для нового варианта используется команда python pipeline.py --output output_v2. Проверка запускается с тем же параметром каталога: python verify_results.py --output output_v2. Сборщик по умолчанию ориентирован на основной output, поэтому для нестандартной папки нужно явно вызвать функцию collect с нужным путём или подготовить архив проверенного каталога отдельно. Результаты второй и третьей лабораторных не следует смешивать в одной папке. У каждой работы собственный код, входные данные и журнал, а общий ключ при необходимости хранится локально и не публикуется.
