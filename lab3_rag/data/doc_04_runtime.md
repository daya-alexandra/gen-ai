# Документ 04. Вызовы API, возобновление и учёт расходов

## Интерфейс обращения к модели

Вторая лабораторная использует функцию make_client и привычный по семинару интерфейс chat.completions.create. В запрос явно передаются response_model и max_retries=3. Число три означает максимум три исправления после первоначальной попытки, то есть не более четырёх ответов на один логический запрос. Это важно при оценке времени и возможных расходов. Ошибки схемы допускают исправление, а ошибка доступа к API не должна автоматически превращаться в четыре одинаковых обращения с неправильным ключом.

Для DeepSeek выбран официальный адрес https://api.deepseek.com; также допускается вариант с окончанием /v1. Другой адрес отклоняется проверкой настроек. Модель задаётся через LLM_MODEL, для подготовленного эксперимента используется deepseek-flash. Режим thinking выключен, ответы запрашиваются в формате JSON. Внутренние автоматические повторы SDK отключены. Благодаря этому число сохранённых попыток не скрывает дополнительных повторов библиотеки, о которых отчёт ничего не знает. При переходе на другую модель нужно отдельно проверить совместимость параметров и расчёт тарифа.

## Где находится ключ

Ключ читается из локального файла .env через переменную LLM_AUTH_TOKEN. Его не включают в исходный код, отчёт, архив результатов и сообщения об ошибках. Файл .env.example содержит только шаблон с PASTE_YOUR_KEY_HERE. Наличие такого шаблона не означает действующего доступа к API. Само создание ключа тоже не гарантирует достаточного баланса на связанном аккаунте. Разрешение использовать чужой учебный ключ следует получать у владельца, а сведения о списаниях проверять в его кабинете или согласованным с ним способом.

Среда настройки загружается сначала из родительской папки проекта, затем из файла рядом с кодом лабораторной. Локальный файл самой работы может переопределить ранее прочитанные значения. Это позволяет хранить общий доступ для нескольких лабораторных и отдельно менять ограничения конкретной работы. Однако при копировании старого .env сохраняются и старые лимиты. Пользователь должен проверить LLM_BUDGET_USD и LLM_MAX_CALLS, а не предполагать, что новые значения из примера автоматически заменили прежнюю конфигурацию.

## Журнал запросов и безопасные ошибки

Каждая полученная попытка записывается в api_trace.jsonl. Событие содержит этап, номер попытки, время, идентификатор ответа, модель, usage, исходный текст ответа и результат валидации. Для контроля происхождения сохраняется хеш запроса. Полные заголовки авторизации и содержимое ключа в журнал не попадают. При сетевой ошибке сохраняются тип исключения и HTTP-статус, если он известен. Текст исключения может содержать лишнюю информацию, поэтому не переносится целиком в пользовательский отчёт.

HTTP 401 обычно означает проблему авторизации, 402 — недостаточный баланс, 429 — ограничение запросов. Но локальная программа не исправляет такие состояния самостоятельно. Она прекращает текущую обработку, сохраняя прогресс, и предлагает проверить ключ, доступ и сеть. После исправления причины пользователь повторяет запуск. Уже принятые ответы не должны оплачиваться заново. Если же был таймаут, неизвестно, успел ли сервер выполнить запрос, поэтому обещать отсутствие списания нельзя. Такая неопределённость отдельно учитывается при резервировании бюджета.

## Кэш и воспроизводимость

Кэш хранит только принятые структурированные ответы. Его ключ зависит от этапа, сообщений, температуры, ограничения длины и конфигурации эксперимента. В конфигурацию входят хеши кода и входных данных, модель, адрес API и режим обработки. Если эти сведения изменились, продолжение в прежней папке отклоняется. Это предотвращает незаметное объединение ответов, полученных на разных версиях промптов или корпуса. Для нового эксперимента необходимо указать отдельный каталог через параметр --output, например output_v2.

При повторном запуске сохранённый ответ ещё раз проходит схему и локальные проверки. Затем он используется без обращения к API. Если основной результат полностью готов, повторное выполнение не должно создавать новые модельные вызовы. Это свойство проверяется интеграционным тестом на заглушке. Кэширование здесь является механизмом повторного использования целого ответа внутри программы. Оно отличается от prompt caching на стороне провайдера, где ускоряется или удешевляется обработка совпадающей части входных токенов, но новый запрос всё равно выполняется.

## Оценка стоимости

В примере настроек второй лабораторной установлен оценочный бюджет один доллар и максимум сто двадцать попыток. Перед отправкой программа резервирует консервативную сумму, используя размер запроса в байтах, дополнительный запас и предельное число выходных токенов. После получения ответа резерв заменяется оценкой по usage. Если usage отсутствует или запрос завершился сетевой ошибкой, резерв не обнуляется. Такой подход уменьшает вероятность, что неизвестная стоимость ошибочно будет принята за нулевую.

Расчёт учитывает входные токены, выходные токены и prompt_cache_hit_tokens. Тарифный снимок взят из официальной документации DeepSeek 19 сентября 2026 года. Для Flash верхняя оценка использует 0,30 доллара за миллион входных токенов без попадания в кэш, 0,006 доллара за миллион входных токенов с попаданием и 1,20 доллара за миллион выходных токенов. Нижняя граница составляет половину верхней. В отчёте показывается диапазон off-peak…peak, а не утверждение о точном списании. Эти значения описывают сохранённую конфигурацию, а не вечный тариф сервиса.

В стоимость полученных ответов включается отдельная диагностика судьи. Налоги, возможные комиссии оплаты и запросы без полученного ответа не входят в эту сумму. Фактические списания нужно сверять с кабинетом провайдера. Программный ограничитель не является банковским лимитом и не защищает другие приложения, использующие тот же ключ. Если владелец ключа запускает параллельный эксперимент в другом месте, его расход не появляется автоматически в локальном budget.json данной лабораторной.

## Измерение времени и завершение

Активное время накапливается по сеансам выполнения, включая этапы обработки и ожидание ответов. Период между остановкой программы и последующим запуском не следует считать временем вычисления. Статус run.json различает подготовку, прерывание, завершение и необходимость содержательной доработки. При низкой второй оценке судьи результат сохраняется со статусом needs_review. Пользователь может прочитать замечания, изменить промпт и начать новый эксперимент в отдельной папке. Старые файлы при этом остаются основанием для сравнения, а не удаляются ради более удобной итоговой картины.
